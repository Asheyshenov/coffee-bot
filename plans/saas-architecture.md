# Coffee Bot → SaaS: архитектура и план перехода

_Дата: 2026-09-28. Исходная точка: ветка `fix/critical-audit-bugs` (критичные баги аудита исправлены, 247 тестов зелёные)._

## 1. Где мы сейчас

Одна кофейня на один запуск: токен бота, креды MWallet, список барист и настройки лежат в ENV. Бот работает через long polling. Фоновые задачи крутятся потоками внутри процесса бота, на каждое уведомление создаётся отдельный `Thread`.

Что уже готово к масштабу:
- денежная логика атомарна: одна оплата даёт один переход статуса и одно уведомление, даже при гонке callback / опроса / истечения счёта;
- суммы хранятся целыми числами в тыйынах;
- статусы защищены CHECK-ограничением в Postgres;
- есть миграции для production, Docker-образ, `pg`.

Что жёстко привязано к одной кофейне:

| Место | Сейчас | В SaaS |
|---|---|---|
| Токен бота | `TELEGRAM_BOT_TOKEN` (4 места) | запись `bots` у арендатора |
| MWallet | `MWALLET_SID/PASSWORD`, читаются в `MWallet::Client#initialize` | запись `payment_accounts` у арендатора, пароль зашифрован |
| Баристы | `BARISTA_WHITELIST` в `AuthService` | таблица `staff` с ролями |
| Настройки | `ORDER_EXPIRE_MINUTES` и др. в ENV | настройки арендатора |
| `clients` | PK = `telegram_user_id` | один человек может быть клиентом нескольких кофеен → `(tenant_id, telegram_user_id)` |
| `drafts` | уникален по `telegram_user_id` | уникален по `(tenant_id, telegram_user_id)` |
| Callback URL | один `/callbacks/mwallet/result` | свой URL на каждый платёжный аккаунт, подпись проверяется паролем этого аккаунта |

## 2. Целевая архитектура

```
Telegram ──webhook──▶ ┌──────────────┐        ┌──────────────┐
                      │  Web (Puma)  │──jobs─▶│ Sidekiq      │──▶ Telegram API
MWallet ──callback──▶ │  stateless,  │        │ (Redis)      │──▶ MWallet API
Админка (браузер) ──▶ │  N копий     │        └──────┬───────┘
                      └──────┬───────┘               │
                             └────────┬──────────────┘
                                  PostgreSQL
```

1. **Один веб-сервис** принимает всё входящее:
   - `POST /tg/:bot_id` — webhook Telegram, проверяется заголовок `X-Telegram-Bot-Api-Secret-Token`;
   - `POST /pay/mwallet/:account_id` — callback провайдера;
   - `/admin/*` — панель владельца кофейни.

   Сервис stateless: его можно запускать в нескольких копиях за балансировщиком. Long polling уходит: он даёт один процесс на бота и не масштабируется.
2. **Sidekiq + Redis** для всего, что ходит во внешние API или делается по таймеру. Обработчик webhook только кладёт задачу и сразу отвечает 200.
3. **PostgreSQL** — единственное хранилище состояния. Одного инстанса хватит на тысячи кофеен (оценка в разделе 6).

### Контекст арендатора

Каждый входящий запрос сначала определяет арендатора: для Telegram по `bot_id` из URL, для callback по `account_id`, для админки по сессии. Результат кладётся в `Tenant.current`. Все запросы к данным арендатора идут через скоуп, например `Order.for_tenant`.

Страховка от утечки данных между кофейнями:
- тест, который проходит по всем моделям и проверяет, что без арендатора запрос падает;
- позже можно добавить Postgres Row Level Security как второй уровень защиты.

## 3. Модель данных

Новые таблицы:

```
tenants          id, slug, name, status(trial|active|suspended), plan, timezone,
                 settings jsonb (время жизни счёта, часы работы, тексты)
bots             id, tenant_id, telegram_bot_id, username, token_enc, webhook_secret, status
payment_accounts id, tenant_id, provider('mwallet'), sid, password_enc, base_url, test_mode, status
locations        id, tenant_id, name, address                  -- на будущее: сеть кофеен
staff            id, tenant_id, telegram_user_id, role(owner|admin|barista), location_id, active
customers        id, tenant_id, telegram_user_id, username, first_name, …  UNIQUE(tenant_id, telegram_user_id)
admin_users      id, email, password_digest / telegram_user_id, tenant_id, role
audit_log        id, tenant_id, actor, action, subject, data jsonb, created_at
subscriptions    id, tenant_id, plan, period_start, period_end, status   -- биллинг
```

`tenant_id NOT NULL` добавляется в `menu_items`, `drafts`, `orders`, `payments`, `payment_operations`, `callback_logs`, `favorite_orders` и `reports`. `order_items` получает арендатора через `orders`.

Уникальные ключи становятся составными:
- `drafts (tenant_id, telegram_user_id)`;
- `orders (tenant_id, merchant_invoice_id)`;
- `invoice_id_provider` уникален в пределах `payment_account_id`.

**Секреты** (токены ботов, пароли MWallet) шифруются AES-256-GCM мастер-ключом из ENV или менеджера секретов. В логах и админке они не появляются.

## 4. Ключевые решения по компонентам

### 4.1 Платежи — главный риск при масштабировании
Сейчас активный счёт опрашивается каждые **2 секунды**. У 1000 кофеен по 3 открытых счёта это около 1500 запросов в секунду к MWallet: такую нагрузку провайдер, скорее всего, заблокирует.

Целевая схема:
- **основной канал — callback.** Код уже исправлен, но callback'и ни разу не доходили в dev. Нужно проверить `result_url` на реальном стенде;
- **опрос как запасной канал, с затуханием:** 5 с, 10 с, 20 с, 30 с, дальше каждые 60 с до истечения счёта. Одна задача Sidekiq на заказ, которая переставляет себя сама;
- **истечение счёта** — задача, запланированная ровно на `created_at + время жизни`, вместо цикла раз в 60 с;
- **поздние оплаты** проверяются после истечения по расписанию: 1 мин, 5 мин, 15 мин, 1 ч, 6 ч, 24 ч.

Выяснить у MWallet:
1. есть ли **API возврата** (сейчас возврат ручной);
2. закрывает ли провайдер счёт по `date_life`. `InvoiceCancel` на тестовом стенде отвечает «Команда не определена», поэтому QR остаётся оплачиваемым;
3. точный список текстовых статусов оплаты для разных мерчантов.

Провайдер оформляется интерфейсом `PaymentProvider` (`create_invoice`, `status`, `cancel`, `refund`, `verify_callback`), чтобы подключать другие банки (MBank, Optima, Элсом) без переделки заказов.

**Юридически.** Деньги должны приходить на договор MWallet самой кофейни, а не на ваш. Иначе платформа становится платёжным агрегатором, а это отдельное регулирование НБ КР. Платформа хранит только креды для выставления счетов.

### 4.2 Telegram
- **Лимиты:** около 30 сообщений в секунду на бота и 1 в секунду в один чат. Все отправки идут через одну задачу `DeliverMessage` с ограничителем на бота (Redis) и повтором по `retry_after` при ответе 429.
- Уведомления переживают перезапуск процесса. Сейчас поток, упавший вместе с процессом, теряет сообщение.
- При подключении бота платформа сама вызывает `getMe` и `setWebhook` с `secret_token`.
- **Персонал** подключается ссылкой-приглашением `t.me/<bot>?start=staff_<одноразовый токен>`. Список Telegram ID вручную больше не нужен.
- **Меню:** стоит перейти с inline-кнопок на **Telegram Mini App** (веб-страница внутри Telegram): фото, модификаторы, корзина, нормальный UX. Бот оставить для уведомлений и работы баристы.

### 4.3 Админка владельца
- **Регистрация кофейни:** создать бота в @BotFather и вставить токен, ввести креды MWallet. Проверка — тестовый счёт на 1 сом.
- **Меню:** категории, размеры, стоп-лист, фото.
- **Персонал:** приглашения и роли.
- **Заказы в реальном времени,** очередь возвратов (поздние оплаты).
- **Отчёты:** выручка, популярные позиции, экспорт CSV.
- **Подписка и оплата сервиса.**

### 4.4 Эксплуатация
- **CI** (GitHub Actions): rspec, rubocop, сборка Docker-образа. Lockfile уже содержит платформы Linux.
- **Окружения:** staging с тестовым мерчантом MWallet и production.
- **Мониторинг:** Sentry для ошибок, метрики (оплаты в минуту, время «оплачен → готов», застрявшие счета, глубина очередей Sidekiq), алерты.
- **Бэкапы Postgres:** ежедневный дамп + восстановление на момент времени (PITR), ежеквартально проверяем восстановление.
- **Логи** в JSON с `tenant_id` и `order_id` (формат уже JSON).
- **Персональные данные:** хранится имя из Telegram и история заказов. Нужны политика конфиденциальности и удаление данных клиента по запросу (Закон КР «Об информации персонального характера»).

## 5. План перехода по шагам

Каждый шаг заканчивается рабочей системой и зелёными тестами. Текущая кофейня становится арендатором №1.

| Шаг | Что делаем | Оценка* |
|---|---|---|
| 1. Арендатор в данных | Таблицы `tenants`, `bots`, `payment_accounts`, `staff`, `customers`; `tenant_id` добавляется nullable и заполняется значением арендатора №1 из текущих ENV, затем NOT NULL; скоупы во всех запросах; креды из ENV переносятся в БД; тест изоляции арендаторов | 1,5–2 нед |
| 2. Webhooks | Один веб-сервис: `/tg/:bot_id`, `/pay/mwallet/:account_id`; `setWebhook` при подключении бота; убрать polling и поток в `bin/bot` | ~1 нед |
| 3. Очередь задач | Sidekiq: отправка сообщений с лимитами, опрос оплаты с затуханием, истечение по расписанию, проверка поздних оплат | 1–1,5 нед |
| 4. Админка (MVP) | Регистрация кофейни, меню, персонал, заказы, возвраты | 3–4 нед |
| 5. Биллинг | Тарифы, пробный период, оплата подписки через MWallet платформы, блокировка при неоплате | 1–2 нед |
| 6. Эксплуатация | CI, staging, Sentry, метрики, бэкапы | ~1 нед, параллельно |
| 7. Mini App | Меню и корзина как веб-приложение внутри Telegram | 2–3 нед |

\* Оценки грубые, для одного разработчика, без учёта ожидания ответов от MWallet.

MVP для первых платящих кофеен — шаги 1–4 и 6, то есть примерно 7–9 недель.

## 6. Оценка нагрузки

Кофейня — около 200 заказов в день. У 1000 кофеен это 200 тыс. заказов в день: в среднем около 2,3 заказа в секунду, в утренний пик примерно в 10 раз больше.

На каждый заказ приходится порядка 10 обращений к боту (меню, корзина, оплата) и 3–5 уведомлений. Итого около 200–300 входящих запросов в секунду в пик. С этим справятся 2–4 копии Puma, один Postgres (db.m-класса) и 2 процесса Sidekiq.

Узкие места по порядку:
1. опрос MWallet — решается затуханием и callback-first;
2. лимиты Telegram на бота — решается ограничителем в очереди;
3. только потом база.

## 7. Решения, которые нужны от владельца продукта

1. **Бот: у каждой кофейни свой или один общий?**
   - *Свой (рекомендую):* свой бренд, свои клиенты, изоляция. Минус: владелец создаёт бота в @BotFather сам (5 минут, инструкция в админке).
   - *Общий бот платформы:* кофейня выбирается по ссылке `t.me/bot?start=<кофейня>`. Проще подключение, но клиенты «ваши», а не кофейни, и одна блокировка бота затронет всех.
   - Архитектура выше поддерживает оба варианта. Решение влияет на порядок работ в шаге 2 и на регистрацию.
2. **Стек админки.**
   - *Rails 8 (рекомендую для SaaS):* авторизация, админ-интерфейс, почта, фоновые задачи из коробки. Цена — переход с Sequel на ActiveRecord или связка `sequel-rails`, около 1 недели при текущих ~7,7 тыс. строк.
   - *Roda/Sinatra + htmx:* без переезда, но авторизацию, формы и прочее придётся писать самим.
3. **Модель оплаты сервиса:** фиксированная подписка, процент с заказа или их комбинация. Влияет на шаг 5 и на то, что считать в отчётах.
